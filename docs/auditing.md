# 操作与登录审计

## 查看入口与权限

- 所有已登录用户：侧边栏「操作与登录记录」，地址 `/#/audit`。
- SuperAdmin：控制台「审计记录」，地址 `/#/admin/audit`，可查看全部记录。
- 个人列表由后端按认证用户 ID 强制过滤。普通用户只能查看列表，不能查看变更详情；两个详情接口均要求 SuperAdmin，普通用户访问返回 403。
- 用户可以查看自己的操作、自己账号的成功或失败登录；别人修改其账号的操作不会作为「自己操作」公开。
- GET `/api/audit/`、`/api/audit/{id}` 为个人接口；GET `/api/admin/audit/`、`/api/admin/audit/{id}` 为管理员接口。
- 列表支持 `pageNumber`、`pageSize`（1–100）、`from`、`to`（含时区）、`module`、`action`、`outcome`、`clientIp`、`targetId`、`userId`、`account`，不返回字段变更明细。
- 管理页面「用户账号 / ID」通过 `account` 接收完整登录账号或用户 GUID，去除首尾空格；账号不区分大小写、精确匹配当前账号或历史账号快照。包含该账号的失败登录，保留旧 `userId` 参数兼容。详情中的「用户 ID」可复制用于筛选，与「记录 ID」「目标 ID」区分。
- SuperAdmin 在个人页面只能查看自己的详情，在管理页面可查看全部详情。
- `userId` 等筛选只能缩小已授权范围，不能扩展范围。查询接口不要求会员权益。

## 记录范围

显式白名单位于 `AuditOperations`。记录登录、注册、资料/密码修改、用户管理、角色与会员调整、卡号与路径、通讯密钥、脚本/片段/素材/数据库数据变更，以及补发和清理指令。

支付订单与回调单独接入，自动会员到期以 System 身份记录。普通查询、审计查询、Token 刷新、素材下载时补写 SHA256、心跳和内部检查时间更新不记录。

`AuditLogs` 保存操作、身份快照、时间、IP、结果与数据状态；`AuditLogDetails` 保存已提交的变更。一次操作的记录 ID 同时作为明细的关联 ID；`TraceId` 可关联应用日志。

记录的用户 ID 不与用户表建立级联外键，删除用户不会删除历史。当前实际数据库外键决定级联删除覆盖范围，审计不会新增业务级联关系。

密码、密码哈希、卡密、连接密钥和素材密码以 `[REDACTED]` 代替；Token 和安全戳不采集。脚本正文、片段内容和 DataJson 仅存长度与 SHA256；普通白名单字段保存前后值，超长字符串截断并标记。不会序列化整个请求、响应、异常消息或文件内容。

登录失败记录关联尝试登录的账号，但 `ActorUserId` 留空，避免把尝试者认定为已经认证的用户。不存在或已被查询过滤器隐藏的账号不关联用户 ID。

## 业务结果与数据状态

- 成功返回和异常传播沿用原业务行为。接口成功不表示客户端已经执行 SignalR 指令。
- 显式事务中的保存只在最终提交后计入明细；回滚/未提交事务不产生成功变更。
- 数据保存后发生通知等后续异常时，结果为失败，数据状态仍可为已提交。
- 多次保存按顺序保留，软删除与物理/级联删除分开标记。
- 采集失败记录 `CaptureIncomplete=true`、`DataStatus=Unknown` 并告警，避免伪装成完整记录。
- 系统卡号过期检查使用批量更新维护内部标记，本轮不纳入用户操作审计。未来新增批量业务写入须显式接入，不能只依赖 SaveChanges 拦截器。

## 上线与配置

新增迁移 `20260930063105_AddAuditLogs` 只创建两张审计表及索引。现有会员与支付迁移需要先应用。API 保留原有启动时执行迁移的逻辑；部署前应备份数据库。开发执行迁移生成使用设计时工厂，不会启动 API 或修改实际数据库。

以下配置可通过环境变量覆盖，无需提交敏感连接信息：

```text
Audit__SpoolDirectory=D:\ToolboxData\audit-pending
Audit__WriteTimeoutSeconds=3
Audit__TrustedProxies__0=10.0.0.2
Audit__ForwardLimit=3
```

`TrustedProxies` 应填写真实代理的直接连接 IP；默认不信任转发头。审计从直接连接地址开始，逆向解析可信代理链，同时保留 ClientIp 和 PeerIp，不改变 RemoteIpAddress 或原限流口径。时间以 UTC Unix 毫秒入库，页面按浏览器本地时区展示。

补写目录默认位于应用输出目录的 `audit-pending`，生产环境应设为不会被重新部署覆盖的持久目录，放在站点静态文件目录以外，只允许服务账号和管理员访问。

## 审计故障与补写

采用业务优先策略：业务结束后，先将脱敏审计以临时文件写入、刷盘并原子改名，然后使用独立数据库上下文写库；成功后移除待补写文件。后台每 30 秒扫描并补写，每轮最多处理 100 个文件。记录 ID 防止重复入库，失败文件保留并记录错误。

审计故障不回滚已经完成的业务，也不重试业务请求。数据库与暂存同时故障时输出 Critical 日志；运维应监控此日志、目录容量及待补写文件积压。请求取消不取消已发生操作的审计入库。

业务提交到审计持久化之间存在进程故障窗口。该策略不能保证所有故障下零丢失；如果需要严格零漏记，应另行改为业务与审计同事务，并接受审计故障阻止业务提交。
